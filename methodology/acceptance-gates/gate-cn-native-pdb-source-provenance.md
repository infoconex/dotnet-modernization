# Gate C-N — Native classic Windows PDB original compiler-source provenance

**Status: PROPOSED / RESEARCH-VALIDATION AUTHORIZED; NOT AN APPROVED RELEASE GATE.**
**Decision authority:** stakeholder Option B, [issue #72](https://github.com/infoconex/dotnet-modernization/issues/72). **Implementation tracking:** [issue #73](https://github.com/infoconex/dotnet-modernization/issues/73). **Reference pilot:** [EXP-043](../../projects/recordsift/evaluations/2026-11-pre-sdk/experiments/EXP-043-five-assembly-pdb-provenance.md), draft PR #71.
**Legacy managed-document checksum Gate C: UNSATISFIED. Source Link production: HOLD.**
**Specification revision:** C-N/0.1-proposed (2026-11-05).

## 1. Claim, nonclaims, and approval state

C-N can attest, for a *specified reproducible build of a specified immutable source revision*, that **every original physical C# compiler source input** was included in the independently enumerated native Windows PDB source-document universe, that the native injected-source checksums match those independently captured **exact compiler-time physical bytes**, and that every corresponding source identity is corroborated by actual structured MSBuild `Csc` task inputs and independent generated-source producer evidence.

This is a **different means of proving a different observable fact** than managed `ISymUnmanagedDocument` checksum API support. C-N does **not** attest that the managed reader exposes checksums, that C13 `NONE` checksum entries contain digests, that Source Link remotely retrieves the correct source, that users can debug with Visual Studio, that a NuGet package was genuinely installed into a Visual Studio project, or that a hostile PDB is safe to parse. The pilot establishes 64 per-assembly source-document records; they are **not** claimed to be 64 distinct source files globally.

**Approval lifecycle** (the status is part of the evidence, not inferred from success):
1. `DESIGN_AUTHORIZED`: stakeholder approved specification development and isolated research validation **only** (#72).
2. `SPECIFIED`: complete proposed requirements, threats, tests, reviewer notes in a DRAFT PR.
3. `RESEARCH_VALIDATED`: bounded live validators and targeted negative controls pass, executing SHA and sanitized evidence captured. This status does **not** activate a release gate.
4. `RELEASE_ACCEPTED`: requires a **new, explicit stakeholder decision** with reviewed scope, limitations, evidence and legacy Gate C disposition.
5. `PRODUCTION_ADOPTION`: separate decision *after* genuine Visual Studio package-project installation and live debugger/source retrieval tests; currently **HOLD**.

A gate validator, green CI job, publication of this specification, or approval of design **cannot advance** stages 4–5.

Never derive the completeness universe from a candidate PDB or the audit report itself. The RecordSift pilot has five production projects. Full normalized identities must be joined in private runner memory; published reports expose only fixed categories and counts, never original source names or hash bytes.

## 3. Security and privacy boundary

**Assumptions:** immutable checked-out trusted source, trusted runner and compiler/toolchain, **locally compiler-produced** PDBs, authenticated pinned packages, reliable source capture and task events. C-N is a build-provenance audit **against this trust boundary**, not independent defense against a malicious build worker, forged CI artifacts, supply-chain compromise, hostile symbol files or malicious path metadata. Do not write a PDB key into a filesystem path or execute it.

**Control obligations:** explicit MSF/DBI/C13/stream/record/identity and length bounds; fail closed on malformed, duplicate or unknown records/algorithms; canonical path mapping; reject ambiguous case-folded paths; verification against original physical bytes (not PDB self-consistency); hash algorithm allowlist and policy; authenticated dependencies and vulnerability advisories; separate constrained reader processes if required; no unapproved native COM; no network during reader execution where possible; no user-controlled destination paths. Polled memory and timeout checks are defense-in-depth, **not** a secure sandbox for arbitrary PDB files. Host and compiler compromise remain out of scope.

Capture originals, private URL manifests, raw task events, preprocessed MSBuild XML, PDBs, per-document hashes and diagnostic logs in an ephemeral private directory **outside** the source checkout. On success **and failure**, unconditionally erase it. Upload only allowlisted sanitized aggregate reports; scrutinize filenames and error messages. Preserve public workflow refs, tool pins, artifact IDs, actual ZIP SHA256, execution SHA and derived counts; retain small durable reports because Actions artifacts expire. No private source, native PDB, full URL, original hash value, sensitive stdout or reader binaries in artifacts.

## 4. Fail-closed verdict and independent review

An individual component can be `VERIFIED`, `INCOMPLETE`, `BLOCKED`, or `FAILED`. The complete **research evidence** can be `PROVENANCE_RESEARCH_VERIFIED` only if *all externally enumerated* components pass CN-01 through CN-11, real executing checks ran and the immutable source/release gates passed. Missing, unsupported, ambiguous, partial, unverifiable or stale observations must **never** be coerced into `VERIFIED`. A verifier `success` report with unauthenticated provenance is not a verified release verdict.

Mandatory test matrix: wrong PDB/PE GUID+age, changed physical source byte, missing/duplicate native named keys, DBI/C13 disagreement, malformed/unknown native record, `NONE` digest misuse, pathmap collision/ambiguous source, missing/duplicate structured Csc task, incorrect actual task input set, generated output already present/wrong producer/bytes, line-less document omitted, managed same-count/different-key identity, missing candidate DLL in a test output, breaking API/consumer/package comparison, missing/suspicious artifact metadata, privacy leak, cleanup failure and mismatched independent component manifest. Negative tests must fail as expected; a green workflow alone is insufficient.

Independent review roles: **architecture** (boundary and portability), **build** (Csc/physical input custody and PE/PDB pairing), **security** (threat model/privacy/advisories and fail closed), **quality** (negative controls and baseline representation), **release governance** (readable decision chain and no implicit policy change). Record reviewer findings with severity, resolution and any disagreements. An independent fresh-context reviewer should analyze the full implementation and outputs, not merely agree with the prior author.

## 5. Secondary sanitized-evidence consistency check

A separate report checker can validate *structural and arithmetic consistency* among the **already-produced** EXP-043 aggregate native and managed-reader JSON outputs, with an externally configured required component set and fixed policy flags. It should reject altered counts, missing keys, false set-agreement booleans, incomplete component statuses and contradictory origin categories. This checks **only the report's internal consistency**; it cannot independently rederive original bytes, prove identity-set equality from counts/booleans, authenticate execution or promote a gate. Its output must be `AGGREGATES_CONSISTENT_RESEARCH_ONLY`, **never** `GATE_C_N_PASSED`. A manual/CI read of the real artifact must also independently verify the ZIP digest and GitHub execution SHA.

The frozen external pilot scope also pins **zero managed checksum exposures for each of the five components** (the verified 0/46), plus the original workflow identity. The secondary validator rejects coordinated nonzero exposure counts between both readers, unchecked free-text privacy/limitation content, and arbitrary diagnostic category text. The job checks the separate GitHub historical workflow run for its ID, SHA, successful conclusion and repository in addition to the artifact ID/hash. These are consistency and provenance-locator controls, **not** independent re-execution of source-byte or document-key verification. Tests changing line-document *counts* must never be described as independent tests changing same-count full document *identities*; that identity guard belongs only to the actual EXP-043 live verifier.

Pilot evidence: [EXP-043 final-head Windows/Ubuntu run 42173080423](https://github.com/infoconex/dotnet-modernization/actions/runs/42173080423), research SHA `9fb67deeb2aa4c98587727abc01e8a11f01070b4`; sanitized artifact `13482117590`, ZIP SHA256 `5efcc9b1c872f85c926eeef4819135a2325d97668b2abdcdde4e21f4b7e14443`. 64/64 native original physical Csc-source matching; managed 46 native line-key documents, 0/46 managed reader checksums, 18 other native documents, 72 C13 `NONE` entries; original 425 API/419 NUnit/5 XML/local package/consumer gates retained. These facts describe the **RecordSift pilot** and are not universal properties of Windows PDBs.

**Required next authorization:** even after the design/tests are reviewed and `RESEARCH_VALIDATED`, get a **separate consolidated stakeholder approval** to accept this as an alternative release gate, explicitly disposing of the managed checksum Gate C requirement. Production Source Link approval, genuine Visual Studio package project install and live source stepping are further independent decisions.
