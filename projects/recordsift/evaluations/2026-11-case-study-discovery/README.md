## Application purpose, consumers and boundaries

RecordSift is a **synchronous, Windows/.NET Framework 4.8, C# 7.3 class library** for importing CSV and XLSX tabular data into caller-defined .NET records, enforcing schema and validation rules, and returning typed results, structured diagnostics and optional reports. It is consumed by another application through public classes and injected source-reader adapters; it is **not** itself a web service, hosted daemon or end-user UI. It does not require Excel installation or a network service for core imports, does not persist imported records, and does not export accepted data records as JSON automatically. [Application README](https://github.com/infoconex/RecordSift/blob/68fdee8210f2cde71674250ce56d110b8ffeeac3/README.md) · [Getting started](https://github.com/infoconex/RecordSift/blob/68fdee8210f2cde71674250ce56d110b8ffeeac3/docs/usage/getting-started.md) · [Architecture](https://github.com/infoconex/RecordSift/blob/68fdee8210f2cde71674250ce56d110b8ffeeac3/docs/engineering/architecture.md).

The caller supplies input ownership, source identifier, schema, explicit property mapping, a decoding/reading adapter, culture as applicable, and positive input budgets. The library owns normalization, validation, result counts, status codes and reporting projections. A caller must independently decide how to use accepted records and protect source data. These responsibilities matter even if the project is already on modern .NET.

## Component and data-flow map

The [solution and project inventory](baseline.md#solution-and-dependency-boundaries) contains five production and five NUnit test projects. Source inspection confirms the important dependency path:

```text
Caller / consumer
  |-- schema + explicit property mapper + input budget + source reader
  |-- CSV TextReader / encoded Stream -> CsvImporter<T>
  |                                  -> ICsvRecordReader -> CsvRecordReaderAdapter (CsvHelper)
  |-- XLSX Stream --------------------> XlsxImporter<T>
  |                                  -> IXlsxWorksheetReader -> XlsxWorksheetReaderAdapter (ExcelDataReader)
  |-- source rows + header/position bindings
               -> Application.RecordValidationPipeline
               -> Domain schema rules, conversions, diagnostics, duplicate/validation rules
               -> TypedImportResult<T> (accepted records, status, counts, diagnostics)
               -> optional Reporting adapters (JSON, diagnostic CSV, readable summary)
```

The caller composes the concrete adapter; there is no required dependency-injection framework. `Domain` has no project dependencies; `Application` depends on `Domain` and owns the input ports; concrete `Infrastructure` implementations depend inward and keep parsing vendors out of core public contracts. [Architecture](https://github.com/infoconex/RecordSift/blob/68fdee8210f2cde71674250ce56d110b8ffeeac3/docs/engineering/architecture.md) · [CSV importer](https://github.com/infoconex/RecordSift/blob/68fdee8210f2cde71674250ce56d110b8ffeeac3/src/RecordSift.Application/Importing/Csv/CsvImporter.cs) · [XLSX importer](https://github.com/infoconex/RecordSift/blob/68fdee8210f2cde71674250ce56d110b8ffeeac3/src/RecordSift.Application/Importing/Xlsx/XlsxImporter.cs) · [Shared validation](https://github.com/infoconex/RecordSift/blob/68fdee8210f2cde71674250ce56d110b8ffeeac3/src/RecordSift.Application/Importing/RecordValidationPipeline.cs).

**Observed code-path detail (source-inspected):** CSV `CsvImporter<T>.Import` validates caller arguments and cancellation, invokes `CsvTableReader.Read`, returns `Failed` for source/schema failures, normalizes rows, then passes them to the shared `RecordValidationPipeline`. XLSX `XlsxImporter<T>.Import` invokes `IXlsxWorksheetReader`, checks selected worksheet/header/bindings and then uses the *same* pipeline. The pipeline validates required/length/pattern values before mapping, then conversion, typed range/custom rules and duplicate identifiers. It creates one of `Completed`, `Stopped` or `Canceled` after processing; separate source failures return `Failed` with no accepted rows. Source-inspected implementations: [CSV](https://github.com/infoconex/RecordSift/blob/68fdee8210f2cde71674250ce56d110b8ffeeac3/src/RecordSift.Application/Importing/Csv/CsvImporter.cs), [XLSX](https://github.com/infoconex/RecordSift/blob/68fdee8210f2cde71674250ce56d110b8ffeeac3/src/RecordSift.Application/Importing/Xlsx/XlsxImporter.cs), [pipeline](https://github.com/infoconex/RecordSift/blob/68fdee8210f2cde71674250ce56d110b8ffeeac3/src/RecordSift.Application/Importing/RecordValidationPipeline.cs), [result invariants](https://github.com/infoconex/RecordSift/blob/68fdee8210f2cde71674250ce56d110b8ffeeac3/src/RecordSift.Domain/Results/ImportResult.cs).

**Important limits of interpretation:** CSV and XLSX eagerly read input; fail-fast does not undo source parsing and cancellation cannot reliably interrupt a vendor read already in progress. `CsvStreamImporterAdapter` handles explicit encoding and decoding errors separately from `TextReader` import. XLSX preflight limits package entries (512), decompressed bytes (at most 64 MiB and 32× the supplied compressed budget), shared strings (one million) and caller-controlled row/column/cell budgets. Those checks are **not** a fixed peak-heap/CPU guarantee or exhaustive malicious-file certification. The source code and [security assessment](https://github.com/infoconex/RecordSift/blob/68fdee8210f2cde71674250ce56d110b8ffeeac3/docs/engineering/release-0.1-security-assessment.md) define these bounded claims.
