## Claims adjudicated against actual upstream source

| Claim | Source evidence and disposition |
|---|---|
| Roslyn Windows-PDB test assertions contain document hashes | **Verified in compiler test source**, NOT execution against RecordSift. [Roslyn PDBEmbeddedSourceTests.cs](https://github.com/dotnet/roslyn/blob/main/src/Compilers/CSharp/Test/Emit2/PDB/PDBEmbeddedSourceTests.cs) explicitly uses `[InlineData(DebugInformationFormat.Pdb)]` and XML `<file ... checksumAlgorithm="SHA1" checksum="...">` expectations. [Roslyn PDBTests.cs](https://github.com/dotnet/roslyn/blob/main/src/Compilers/CSharp/Test/Emit2/PDB/PDBTests.cs) contains numerous `format: DebugInformationFormat.Pdb` source SHA1 expectations. The compiler generally emits checksum-bearing documents, but **specific candidate physical records still unmeasured**. |
| Cecil's CCI parser obtains algorithm GUID/digest from named source streams | **Verified in source.** [jbevain/cecil symbols/pdb/Microsoft.Cci.Pdb/PdbFile.cs](https://github.com/jbevain/cecil/blob/master/symbols/pdb/Microsoft.Cci.Pdb/PdbFile.cs) `LoadInjectedSourceInformation` reads source GUIDs and checksum bytes. Its `ReadSourceFileInfo` enumerates `DEBUG_S_SUBSECTION.FILECHKSMS`, consumes the index/length/type (not actual checksum byte contents), then optionally reads `/SRC/FILES/<UPPERCASE FILENAME>` stream for exact managed algorithm/bytes. This is consistent with our prior source concerns; **not proof that frozen PDB's FILECHKSMS inventory can be traversed**. |
| Cecil exposes these values in its managed document model | **Verified source capability.** [jbevain/cecil symbols/pdb/Mono.Cecil.Pdb/NativePdbReader.cs](https://github.com/jbevain/cecil/blob/master/symbols/pdb/Mono.Cecil.Pdb/NativePdbReader.cs) is C#; `NativePdbReader.ProcessDebugHeader` matches RSDS GUID before `PdbFile.LoadFunctions`; its `GetDocument(PdbSource)` assigns `HashAlgorithmGuid=source.checksumAlgorithm` and `Hash=source.checksum` on a Mono.Cecil `Document`. Despite the **NativePdbReader** name, this is a **managed Windows PDB reader**; the **writer** is a separate potential COM case. [Cecil's symbol documentation](https://github-wiki-see.page/m/jbevain/cecil/wiki/Debug-symbols) also describes the managed reader and COM-based writer. |
| Cecil and Microsoft CCI are independent parsers | **Not independent.** Cecil **vendors Microsoft.Cci.Pdb** code. Comparing Microsoft CCI to Cecil does not provide independent decoding evidence. dnlib's managed reader and Cecil/CCI provide distinct implementations but share format assumptions; require actual byte equality and ideally an independently instrumented PDB stream layout inventory. |
| Roslyn calls the native symbol writer for Windows PDB document data | **Supported at higher-level API** by [Roslyn NativePdbWriter](https://source.dot.net/Microsoft.CodeAnalysis/NativePdbWriter/PdbWriter.cs.html) and [SymUnmanagedWriter](https://source.dot.net/Microsoft.CodeAnalysis/DiaSymReader/Writer/SymUnmanagedWriter.cs.html). **Not established:** exact lower-level native binary serialization or which physical writer DLL and security patch level was loaded in EXP-024 CI; do not assert its byte layout is definitively known/unknown from this alone. |
| LLVM and DIA were examining a different inventory | **Plausible, not proven root cause.** Existing EXP-029/033 record `(no checksum)` and **zero text indicators** of C13 checksum in an LLVM output; EXP-035 DIA source rows yielded 0/4 actual managed hashes. None of these establishes absence of managed checksum records. Full PDB binary and direct independent read still required. |
| `Microsoft.DiaSymReader.Tools.PdbToXmlConverter` is a path to managed checksum records | **Source-supported as a Roslyn test mechanism, execution-security UNVERIFIED.** It uses managed interfaces into a Windows PDB reader. Treat any runtime dependency on native Microsoft DiaSymReader as subject to same exact patch/provenance restrictions as EXP-031; neither built-in nor packaged means automatically patched. No converter was executed. |
| A `dnlib.net` malicious NuGet package exists | **Credible and independently corroborated, not the genuine `dnlib` package.** [ReversingLabs detection](https://secure.software/nuget/packages/dnlib.net) and [malware record MAL-2024-4472](https://o3.security/malware/nuget/dnlib.net) associate the lookalike `dnlib.net` with supply-chain malware. The genuine [dnlib NuGet](https://www.nuget.org/packages/dnlib) is a different ID and owner; a trusted feed and exact ID/version/hash must be enforced. This does **not** establish genuine dnlib is vulnerability-free. |
| A C# 7.3 + net48 fixture covering SHA1/SHA256, varied encodings and negatives is warranted | **Strong, proportionate targeted hypothesis, UNEXECUTED.** Roslyn CLI documents `/checksumalgorithm:SHA1` default and SHA256 option. However, fixture portability, the actual compiler-input byte interpretation (BOM, physical encoding, generated code), parser APIs, explicit PDB pairing, and controls must be precisely specified; a fixture pass does not prove frozen RecordSift artifact success. |
| Differential tests with three readers | **Qualify for safety and independence.** Start with **two independently implemented fully managed readers**: dnlib vs Cecil/CCI, avoiding native COM initially. A third Microsoft native reader is *optional and gated on verified patch provenance*, not part of a required first run. Do not use old security-blocked native NuGet packages or make the whole pilot depend on COM being available. |
| Checksum authenticity is a required Source Link gate | **Important open stakeholder policy/goal question.** Existing [outstanding gate procedure](remaining-source-link-approval-gates.md) explicitly requires actual managed document checksum authenticity (Gate C); it is a **chosen stringent research acceptance criterion**, not yet independently established as an inherent prerequisite for all Source Link functionality. **Do not silently remove it**. Distinguish (a) source URL mapping, (b) source identity/bytes, (c) debugger stepping with network retrieval, (d) document-checksum audit. Reclassify priority only with approved decision record and compensating controls. Matching SHA1 metadata demonstrates consistency of that metadata with measured source bytes under the selected hash, not a standalone cryptographic trust chain nor anti-tampering guarantee. |

## Exact source-to-structure trace confirmed in this review

1. [dnlib managed reader](https://github.com/0xd4d/dnlib/blob/master/src/DotNet/Pdb/Managed/PdbReader.cs) reads the MSF7 streams, source paths, checksum algorithms and bytes via [DbiDocument.cs](https://github.com/0xd4d/dnlib/blob/master/src/DotNet/Pdb/Managed/DbiDocument.cs), but discovers documents in [DbiModule.ReadFiles](https://github.com/0xd4d/dnlib/blob/master/src/DotNet/Pdb/Managed/DbiModule.cs) when FileInfo (`0xF4`) file-index records are encountered. `PdbReaderOptions.None` selects managed parsing; exact frozen PDB compatibility unknown.
2. [Cecil CCI PdbFile.cs](https://github.com/jbevain/cecil/blob/master/symbols/pdb/Microsoft.Cci.Pdb/PdbFile.cs) independently proves an alternate **source-level implementation route**, but relies on native FILECHKSMS subrecord enumeration to *locate* files and `/SRC/FILES/` to obtain physical managed hashes. Its C# [NativePdbReader.cs](https://github.com/jbevain/cecil/blob/master/symbols/pdb/Mono.Cecil.Pdb/NativePdbReader.cs) maps PdbSource hash fields to `Document.HashAlgorithmGuid` / `Hash`.
3. [Roslyn PDBEmbeddedSourceTests](https://github.com/dotnet/roslyn/blob/main/src/Compilers/CSharp/Test/Emit2/PDB/PDBEmbeddedSourceTests.cs) provides an actual upstream expected output for `DebugInformationFormat.Pdb` with SHA1; it **does not certify current RecordSift output**.

## Recommended smallest next experiment, pending existing authority and security preflight

**One disposable multi-reader fixture pilot** rather than a monolithic Source Link rerun. Conduct a documentation-first dependency/asset and security preflight before executing any new reader. Pin exact dnlib and Cecil package/source versions and hashes, verify actual package ID and approved source, and keep **all new dependencies exclusively within isolated research tooling**.

1. In a temporary minimal C# 7.3/net48 project compile **classic Windows PDB** with exactly captured compiler executable path/version, `/debug:pdbonly`, explicit `/checksumalgorithm:SHA1`, and controlled source files (BOM, UTF-8 without BOM, CRLF). Record actual compiler-input SHA1 and full file identities.
2. Confirm PE/PDB CodeView GUID/age, PDB MSF type, compiler source path remapping and source-tree commit; produce SHA256 variation as a separate independently identified fixture, not an implicit mode.
3. Run **dnlib managed** and **Cecil managed** readers independently on the same PE/PDB, constrained by low-privilege, no-network-at-runtime, trusted input, file-size bounds, process time/memory limits and fail-closed errors. Verify actual selected document paths, digest algorithm GUID, full hash bytes, and exact checksum matching; do not infer from document count or `(no checksum)` text.
4. Negative controls: one altered physical source byte **after** compilation must mismatch without modifying PDB; wrong matching-PDB pairing must fail; missing file/source mapping/unsupported checksum must show an explicit inconclusive or fail-closed state. Corrupted PDB input only if bounded preflight and safety review authorize it.
5. If fixture read works, run on the **existing frozen RecordSift source/output** in a clean disposable checkout and compare **four selected owned CSV documents**, not exactly four total PDB files, accounting for observed checkout bytes and actual compiler-invocation conditions.
6. If two readers disagree, log only bounded categories, capture no private binary/source, examine format assumptions. Do not count Cecil and CCI as independent confirmations; native Microsoft reader remains optional and security-gated.

**Initial verdict:** credible but **NOT EXECUTED**. Preserve EXP-035 (0/4 managed checksums **INCONCLUSIVE**), EXP-031 native reader **SECURITY-BLOCKED**, VS PMC and debugger gates **NOT TESTED** and Source Link **HOLD**. No main changes, PR merge, package install/publish or application dependency changes. Any gate-policy revision requires explicit stakeholder review and approval.
