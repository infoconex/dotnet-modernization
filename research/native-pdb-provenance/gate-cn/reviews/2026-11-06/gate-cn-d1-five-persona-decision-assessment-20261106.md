## Primary recommendation

**Recommend Option A:** explicitly authorize only D1 isolated **disposable synthetic negative-control research**, with these boundaries:

1. **Scope:** 11 targeted tests drawn from the 17-design matrix in the [P0 plan](gate-cn-p0-targeted-verification-design-20261106.md): M-N01..05, B-N01/B-N02/B-N04 (mock-only package selection), I-N01/I-N03/I-N05. Include positive companions; no RecordSift builds and no real native PDB mutation in D1.
2. **Method:** requirements-first and test-first; domain-defined immutable manifest/component/compilation/identity contracts. Build only research-only adapters necessary to make these narrowly scoped controls executable. Do not modify or reclassify the existing live provenance validator as production-ready. No release-capable verifier or production gate workflow is authorized.
3. **Witness quality:** each test must identify one controlled change, expected fixed failure category, positive baseline, exact validator/tool version, actual observed exit/status and any unrelated setup errors. A failing test is not automatically a successful negative; unrelated or inconclusive failures do not count.
4. **Privacy/trust:** synthetic source and binaries only; no real RecordSift/PDB/private compiler captures; CI least privilege, ephemeral temporary directories, no uploaded raw paths/source/credentials, allowlisted fixed-category sanitized metadata and cleanup on success/failure. No use of review artifacts to self-authorize.
5. **Evidence:** preregistered named test matrix and branch/SHA, actual CI run SHA/conclusion, test counts and individual categories, change/review history, immutable sanitized evidence and tests retained under the draft research branch. Distinguish source-observed gap, hypothetical exploit, and demonstrated failure. Keep all P0 acceptance checkboxes open until genuinely verified.
6. **Stop at D1:** report exact passes/fails and residual untested live scenarios, then request a **separate explicit D2 scope decision** with the smallest non-RecordSift single-project net48 Windows native-PDB build and targeted real negatives. Do not reuse/expand authorization silently.

## Exit criteria and unresolved policy

- **D1 successful research outcome:** all 11 controls plus paired positive cases execute as planned, failures occur at their intended stage, and evidence is anchored to exact execution SHA and sanitized by policy. This proves **synthetic checks only**.
- **D1 partial / failure:** any weak/ambiguous negative, bypass, unsupported fixture behavior or privacy leak leaves that requirement OPEN; document observed failure and remediate only inside approved research boundaries, without broadening scope.
- **D1 never sufficient for:** independently signed production manifest, true non-self-approved organizational authority, fresh genuine Csc-to-DLL/PDB attribution, real native-PDB corruption handling, installed NuGet selection, CLR runtime module binding, human acceptance, Gate C waiver or Source Link production.
- **D2 authority:** D1 approval does **not** approve a real Windows PDB build, a new broad fixture matrix or production implementation. Formal D2 scope requires a separate request.
- **Organizational authority:** named human technical/security/quality/release reviewers, independent evidence custodian, retention and revocation rules remain OPEN in [#77](https://github.com/infoconex/dotnet-modernization/issues/77); this synthetic persona analysis is not a substitute.
