# Documentation templates

Read the [authoritative first-contact protocol](../methodology/evaluation-process.md#start-here-first-contact-protocol) **before starting** a new application evaluation. Inspect existing evidence, interview only for missing stakeholder decisions and obtain explicit scope approval before investigations. Then adapt the [evaluation overview](evaluation-overview.md) template, using the [baseline variation guide](../methodology/baseline-variation-guide.md) to check relevant alternatives for every field without copying unobserved possibilities into the baseline. For substantial applications, use the [application baseline](application-baseline.md) template to record source-backed repository/solution/project discovery **and** reproducible compatibility verification; small evaluations may keep the same relevant facts in their overview rather than creating another file. Screen relevant areas using the [investigation catalog](../methodology/investigation-catalog.md); do not create work or empty documents for inapplicable areas. For each meaningful hypothesis, use the [experiment record](experiment.md) template.

For hands-on technical discovery, follow the [step-by-step guide](../methodology/technical-discovery-runbook.md). Record actual findings, prerequisite versions and command results in the **single [discovery report template](application-baseline.md)**. Do not create a separate execution log. Consider scripts only after native commands have been tried and their applicability understood.

When editing templates, write angle-bracket placeholders as inline code (for example, `<project>`) so Markdown does not interpret them as HTML. Remove unused example rows when populating an actual application baseline.

These are lightweight examples, not required empty files. Copy them into a real dated evaluation and replace placeholders with the actual repository SHA, environment inventory, commands, observed results, evidence and limitations.

The [methodology](../methodology/README.md) specifies minimum evidence standards. When assessing shared .NET settings and tooling, consult the [repository configuration assessment](../methodology/repository-configuration.md) and record only applicable findings. Keep research findings, engineering decisions and implemented changes separate, and do not turn a successful isolated experiment into an unqualified implementation claim.
